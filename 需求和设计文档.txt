# KSP Mod Localization Tool

一个用于自动扫描 **Kerbal Space Program（KSP1）Mod**、提取可本地化文本、生成 KSP Localization 文件，并通过 **OpenAI Compatible API** 辅助完成简体中文翻译的 Python 工具。

项目目标不是简单的“批量替换字符串”，而是逐步构建一个：

> **安全、可回滚、可审计、可增量运行、支持 AI 翻译、适用于大型 KSP Mod 的本地化工具。**

---

# 1. 项目目标

KSP Mod 通常包含大量 `.cfg` 文件，其中存在：

```text
PART
RESOURCE_DEFINITION
SUBTYPE
VARIANT
EXPERIMENT
STRATEGY
...
```

等 ConfigNode。

这些节点中包含大量面向玩家显示的英文文本，例如：

```cfg
PART
{
    name = exampleEngine

    title = Example Engine
    manufacturer = Example Industries
    description = A powerful liquid fuel engine.
    tags = engine rocket liquid
}
```

本工具负责将这些文本转换为 KSP Localization 格式：

```cfg
Localization
{
    en-us
    {
        #LOC_EXAMPLE_exampleEngine_title = Example Engine
        #LOC_EXAMPLE_exampleEngine_manufacturer = Example Industries
        #LOC_EXAMPLE_exampleEngine_description = A powerful liquid fuel engine.
        #LOC_EXAMPLE_exampleEngine_tags = engine rocket liquid
    }
}
```

同时修改原始 CFG：

```cfg
title = #LOC_EXAMPLE_exampleEngine_title
```

然后通过 AI 将英文 Localization 翻译为：

```cfg
Localization
{
    zh-cn
    {
        #LOC_EXAMPLE_exampleEngine_title = 示例发动机
        #LOC_EXAMPLE_exampleEngine_manufacturer = 示例工业
        #LOC_EXAMPLE_exampleEngine_description = 一台强力的液体燃料发动机。
        #LOC_EXAMPLE_exampleEngine_tags = 发动机 火箭 液体
    }
}
```

# 4. 安全原则

这是本项目最重要的设计原则。

工具会直接修改 KSP Mod 文件，因此：

> **任何修改原文件的操作都必须可以追踪、恢复和验证。**

## 4.1 永远先备份

修改：

```text
engine.cfg
```

之前必须创建：

```text
engine.cfg.bak
```

例如：

```text
Parts/
├── engine.cfg
└── engine.cfg.bak
```

备份应该使用 Python 的：

```python
shutil.copy2()
```

尽量保留：

* 文件内容
* 文件时间戳
* 文件权限信息

---

# 5. Backup 策略

需要避免反复运行产生：

```text
engine.cfg.bak
engine.cfg.bak.bak
engine.cfg.bak.bak.bak
```

默认策略：

```text
原文件：
engine.cfg

首次运行：
engine.cfg.bak

再次运行：
不要覆盖已有 .bak
```

因为 `.bak` 应代表：

> **第一次修改之前的原始文件。**

未来可以增加：

```text
--force-backup
```

允许显式创建新的备份。

也可以未来支持：

```text
backup/
    20260916_215400/
        engine.cfg
        tank.cfg
```

但当前版本优先保持简单。

# 6. 修改原始 CFG

原始：

```cfg
PART
{
    name = exampleEngine

    title = Example Engine
    description = Powerful engine.
}
```

修改：

```cfg
PART
{
    name = exampleEngine

    title = #LOC_EXAMPLE_exampleEngine_title
    description = #LOC_EXAMPLE_exampleEngine_description
}
```

必须保留：

* 缩进
* 换行
* 其他字段
* ConfigNode 结构
* 注释
* 文件编码

尽量只修改目标字段的 value。

---

# 7. 已本地化字段必须跳过

如果原文件已经是：

```cfg
title = #LOC_EXAMPLE_ENGINE_TITLE
```

则不能再次生成：

```cfg
title = #LOC_EXAMPLE_exampleEngine_title
```

检测：

```python
value.startswith("#LOC_")
```

即可作为第一层判断。

未来可以增加更加严格的 Localization Key 检测。

---

# 8. 当前安全字段

第一版只处理：

```text
PART
 ├── title
 ├── description
 ├── manufacturer
 └── tags
```

不要因为发现：

```cfg
MODULE
{
    title = Something
}
```

就自动提取。

原因是 KSP Mod 中很多 `name`、`title` 等字段实际上可能参与模块逻辑，而不是玩家显示文本。

例如：

```cfg
MODULE
{
    name = ModuleSomething
    title = Something
}
```

不能假定 `title` 一定安全。

---

# 9. ConfigNode 解析

第一版使用简单的文本扫描 + 大括号深度。

当前逻辑能够正确处理：

```cfg
PART
{
    name = example

    title = Example

    MODULE
    {
        title = Do Not Extract
    }
}
```

只提取：

```text
PART.title
```

不提取：

```text
PART.MODULE.title
```

---

# 10. 长期解析方案

随着项目支持更多 Mod，应该逐渐从：

```text
正则表达式 / 文本扫描
```

升级为：

```text
真正的 KSP ConfigNode Parser
```

原因：

KSP CFG 并不是普通 INI。

需要正确处理：

* 嵌套 Node
* 重复字段
* 注释
* 引号
* 特殊字符
* 多行内容
* Unicode
* 文件编码
* 条件节点
* ConfigNode 特有格式

原则：

> 不要为了支持更多字段而无限增加正则表达式。

# 11. Localization Key 设计

默认格式：

```text
#LOC_<PREFIX>_<IDENTIFIER>_<FIELD>
```

例如：

```text
#LOC_BDB_fooEngine_title
#LOC_BDB_fooEngine_description
#LOC_BDB_fooEngine_manufacturer
```

其中：

```text
PREFIX
```

由用户指定，例如：

```text
BDB
RESTOCK
NFM
MYMOD
```

---

# 12. Key 唯一性

必须确保不同字符串不会生成相同 Key。

例如：

```text
PART:
    name = engineA

PART:
    name = engineB
```

应该得到：

```text
#LOC_MYMOD_engineA_title
#LOC_MYMOD_engineB_title
```

如果发现重复：

```text
#LOC_MYMOD_engineA_title
```

不能静默覆盖。

必须：

1. 记录 WARNING
2. 保留冲突信息
3. 尽可能生成稳定的备用 Key
4. 日志中明确说明

# 13. OpenAI Compatible API

AI 翻译层不能绑定某一家 AI 服务。

使用 OpenAI Compatible API。

Python SDK：

```python
from openai import OpenAI
```

配置：

```json
{
    "base_url": "http://127.0.0.1:8317/v1",
    "api_key": "sk-xxxx",
    "model": "model-name",
    "batch_size": 50,
    "temperature": 0.1
}
```

这样可以支持：

* OpenAI
* LiteLLM
* Grok2API
* cliproxyapi
* New API
* One API
* 其他 OpenAI Compatible 服务

建议：

```text
translator.json
```

例如：

```json
{
    "base_url": "http://127.0.0.1:8317/v1",
    "api_key": "sk-xxxx",
```

# 15. AI 翻译批处理

不能：

```text
一条文本 = 一次 API 请求
```

大型 Mod 会产生大量请求。

应该批量：

```json
[
    {
        "key": "#LOC_MYMOD_engine_title",
        "text": "Super Engine"
    },
    {
        "key": "#LOC_MYMOD_engine_description",
        "text": "A powerful engine."
    }
]
```

例如每批：

```text
50 条
```

由：

```json
"batch_size": 50
```

控制。

---

# 16. AI 输出必须是结构化数据

推荐要求 AI 返回：

```json
[
    {
        "key": "#LOC_MYMOD_engine_title",
        "text": "超级发动机"
    },
    {
        "key": "#LOC_MYMOD_engine_description",
        "text": "一台强力的发动机。"
    }
]
```

不要要求 AI 返回：

```text
翻译如下：

xxx
xxx
```

否则解析困难。

# 17. AI System Prompt

基本原则：

```text
You are a professional KSP mod localization translator.

Translate English into Simplified Chinese.

Rules:

1. Preserve every localization key.
2. Do not add or remove entries.
3. Return valid JSON only.
4. Do not explain your answer.
5. Preserve numbers, units, identifiers and technical names.
6. Preserve KSP terminology consistently.
7. Do not translate internal identifiers.
8. Translate player-facing text naturally.
```

未来通过 Glossary 动态追加术语表。

---

# 18. AI 翻译失败处理

API 失败不能导致整个项目崩溃。

例如：

```text
Batch 1  OK
Batch 2  OK
Batch 3  FAILED
Batch 4  OK
Batch 5  OK
```

应该：

```text
记录 Batch 3 FAILED
继续 Batch 4
继续 Batch 5
```

最终报告：

```text
Total:      250
Translated: 200
Failed:      50
```

失败的文本保留英文。

---

# 19. API Retry

网络错误、429、502、503 等临时错误应该重试。

建议：

```text
第一次失败
等待 2 秒

第二次失败
等待 4 秒

第三次失败
等待 8 秒

仍然失败
记录错误并跳过
```

最大重试次数配置：

```json
{
    "max_retries": 3
}
```

不要无限重试。

---

# 20. Translation Cache

必须避免同一文本反复调用 AI。

例如：

```json
{
    "Super Engine": "超级发动机",
    "Fuel Tank": "燃料箱",
    "Reaction Wheel": "反应轮"
}
```

文件：

```text
translation_cache.json
```

流程：

```text
发现文本
    ↓
查询 Cache
    ↓
存在？
 ├── YES → 直接使用
 └── NO  → AI 翻译
              ↓
           写入 Cache
```

---

# 21. Translation Memory

长期应该将简单 Cache 升级成 Translation Memory。

推荐记录：

```json
{
    "source": "Super Engine",
    "target": "超级发动机",
    "source_language": "en-us",
    "target_language": "zh-cn",
    "model": "model-name",
    "timestamp": "...",
    "verified": false
}
```

这样未来可以区分：

```text
AI 自动翻译
人工确认翻译
术语表翻译
```

# 23. 翻译质量检查

AI 返回结果后必须验证。

至少检查：

## Key 数量

输入：

```text
50
```

输出必须：

```text
50
```

否则判定异常。

---

## Key 完整性

输入：

```text
#LOC_X_engine_title
```

输出必须仍然存在：

```text
#LOC_X_engine_title
```

---

## 数字

例如：

```text
Engine produces 250 kN
```

不能莫名丢掉：

```text
250
```

---

## 单位

例如：

```text
250 kN
1.5 t
10 %
```

必须尽可能保持。

---

## 格式符

未来需要保护：

```text
{0}
{1}
%s
```

以及 KSP 特有格式。

# 32. 增量更新

第一次：

```text
2187 strings
```

Mod 更新后：

```text
2204 strings
```

不能重新翻译全部 2204 条。

应该识别：

```text
17 new strings
```

只发送：

```text
17
```

条。

# 33. 增量判断

建议基于：

```text
LOC Key
+
English Source Text
```

进行判断。

例如：

```text
#LOC_MYMOD_engine_title
Super Engine
```

如果英文变成：

```text
Super Engine Mk2
```

应该认为是新的待翻译内容。

因此不能只使用：

```text
key
```

作为缓存判断条件。

# 36. KSP 节点规则

未来应该使用规则配置，而不是把所有逻辑硬编码进 Python。

例如：

```json
{
    "PART": [
        "title",
        "description",
        "manufacturer",
        "tags"
    ],
    "RESOURCE_DEFINITION": [
        "displayName",
        "abbreviation"
    ],
    "VARIANT": [
        "displayName",
        "description"
    ],
    "SUBTYPE": [
        "title",
        "descriptionSummary",
        "descriptionDetail"
    ]
}
```

这样以后增加节点不需要修改核心解析器。

# 38. 不应该做的事情

Agent 开发时禁止为了“快速实现”采取以下方式：

## 不要

```text
rm -rf
```

或类似批量删除整个 Mod。

## 不要

未经备份就直接重写 CFG。

## 不要

把整个 CFG 重新格式化。

## 不要

用全局：

```text
title =
```

正则替换所有 title。

## 不要

修改 MODULE 内部字段，除非明确加入对应规则。

## 不要

为了修复一个解析问题而删除原来的测试。

## 不要

把 API Key 写死在源码。

# 49. 最终目标

最终这个项目应该成为一个真正的：

> **KSP Mod Localization Pipeline**

而不是一次性的翻译脚本。

目标工作流：

```text
下载 KSP Mod
       ↓
指定 Mod 目录
       ↓
扫描
       ↓
自动识别可本地化文本
       ↓
检查已有 Localization
       ↓
生成稳定 LOC Key
       ↓
备份原 CFG
       ↓
安全修改 CFG
       ↓
生成 en-us.cfg
       ↓
Translation Memory
       ↓
Glossary
       ↓
OpenAI Compatible AI
       ↓
自动翻译
       ↓
质量检查
       ↓
生成 zh-cn.cfg
       ↓
日志 + Manifest
       ↓
完成
```

最终用户只需要：

```bash
python localizer.py \
    --mod ./GameData/MyMod \
    --prefix MYMOD
```

就可以完成整个 Mod 的本地化准备工作。

# 51. 项目设计理念

本项目最重要的不是“AI 翻译得多快”，而是：

```text
Correctness
Safety
Reproducibility
Auditability
Incremental Processing
Translation Consistency
```

也就是说：

> **宁可少自动化一点，也不要因为自动化而破坏 Mod。**

AI 翻译可以错。

Localization 可以重新生成。

但是：

> **原始 Mod 不应该因为这个工具而不可恢复。**
